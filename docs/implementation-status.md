# 実装範囲: 三種類の接続と相手ごとの経路選択

更新日: 2026-10-21。`docs/design.md`・`protocol.md`・`sdk.md`・`validation.md`は将来の設計を含みます。実行版の正確なメッセージ形式と制限は[prototype.md](../protocol/prototype.md)を参照してください。

公開サーバー向けに、認証付きHTTPSの背後でWebRTCを使うモードを追加しました。構成とインターネット越しの確認結果は[公開サーバー](deployment.md)を参照。以下は通常のローカル起動についての記録です。

## 任意データの配送から使い始める

今回の実装では、任意データの順序付き配送を土台にしました。指定チャットの最後の方針に従い、`state`を使わずに参加できます。データの意味、競合処理、保存、キャンバスやゲームの初期状態の作成は、アプリ側で決めます。

共通の中継サーバーはGoです。WebRTCとQUICを直接終端し、C#は公式LiteNetLibを使う.NETプロセスから内部WebSocketを通じて接続します。三方式とも同じ部屋へ参加します。アプリ固有の型やゲームのルールはサーバーへ組み込んでいません。

| 機能 | 今回の実装 |
| --- | --- |
| メッセージ | MessagePack、部屋内の順序付き配信、操作IDによる重複排除。大きい値は自動分割し、復元・検証後に一度だけ通知 |
| 宛先付きpeer配送 | `sendTo`で任意の値を特定の相手へ配送。ブラウザ間P2Pまたは中継で、受信確認・再送・重複排除・送信者とトピックごとの順序を管理。コア連番・履歴から独立 |
| 共有状態 | 任意参加。set/delete、版を条件にするCAS、削除版の保持、参加時の状態取得 |
| アプリの初回同期 | チェックポイントと後続操作を、必要なら分割して取得。JSの`follow`は受信を先に登録し、重複を除いて順に適用。途中データは公開しない |
| 位置などの更新 | 送信者・接続世代・キー・連番で新旧を判定。対応ブラウザ間はWebRTC直結を試し、その他は中継。切断時は中継へ復帰 |
| イベント | 現在の参加者へ配信。待機中の期限切れを破棄 |
| バイナリ転送 | 分割、受信許容量の通知、キャンセル、サイズ・SHA-256確認。保存先は呼出側のストリーム |
| ライブデータ | 小さなバイト列の期限付き配信。動画全体の配信機能は未実装 |
| 通信統計 | 接続方式、アプリの送受信バイト数、送信待機量、破棄数。相手ごとの経路・理由・直結の送受信数・往復時間。未取得のRTTはnull |

## データ全体と通信片の上限を分ける

| 対象 | 上限 |
| --- | --- |
| 部屋数 / 一部屋の参加者 | 64 / 32 |
| 一つの論理メッセージ | 既定4 MiB。MessagePackの外枠も含む |
| 分割時の通信片 | 既定12 KiB、設定上限16 KiB。外枠は別 |
| 一回の通信フレーム | 64 KiB。既存blobチャンクは再分割しない |
| 位置・ライブ更新全体 | 1,000 bytes。中継メタデータ分も必要 |
| 一部屋の共有状態 | 256キー、既定2 MiB。削除版も含む |
| チェックポイント | 既定2 MiB / 部屋 |
| アプリ操作の履歴 | 直近256件かつ既定4 MiB / 部屋 |
| 操作IDの重複排除 | 直近512件かつ既定4 MiB / 部屋 |
| ファイル転送 | 64 MiB / 転送、一部屋で同時4件 |
| 一つの転送チャンク | 12 KiB |
| 受信許容量 | 未消化分64 KiB以下 |
| 分割転送の受信予約 | 既定8 MiB / 接続、同時4転送 |
| 信頼性のある送信待機 | 既定8 MiB / 接続 |
| 分割転送の未確認データ | 既定64 KiB / 転送 |
| 分割転送の期限 | 開始から既定30秒。進捗で延長しない |
| SDKのアプリ受信待ち | 件数に加え、符号化サイズをもとにバイト数でも制限 |
| サーバー全体の保持データ | 既定64 MiB |
| サーバー全体の転送用予約 | 既定64 MiB。送信待機と組立領域を合計 |

上限は[`config/limits.example.json`](../config/limits.example.json)を参考に設定でき、サーバーは`--limits <JSONのパス>`または`KOKOSYNC_LIMITS`から読みます。SDKの`fragmentation`設定とサーバーの設定を接続時に照合し、小さい側を採用します。上限内でも、共有状態の合計や送信待機容量が不足すれば操作を拒否します。

容量予算は符号化したデータと予約バッファを管理する値です。復号後のオブジェクト、ランタイム、通信ライブラリの使用量を含むプロセス全体のメモリと同じ値ではありません。大きなファイルを全体展開せずに処理する場合は、ストリーム型の`sendBlob`を使います。

送出は制御・状態・イベント・通常メッセージの順序をそれぞれ管理し、大容量データの通信片の間に他の種類の通信を挟みます。位置・ライブ更新は独立して送れます。同じ順序付きメッセージ列の後続データは先行データを追い越しません。

初回参加の状態は完全に復元してから公開し、途中で届いた後続更新が追い越さないようにします。組立失敗、期限切れ、キャンセル時は途中データを破棄します。順序付きデータを欠落させたまま継続できない場合は、接続を終了して再参加を必要とします。これは公平制御や帯域保証を完成させたものではありません。

## 接続方式ごとの制約を確認する

| 経路 | 状態・操作・ファイル | 位置・ライブ |
| --- | --- | --- |
| ブラウザ↔Go | WebRTC ordered DataChannel | unordered / 再送なしの別DataChannel |
| Go↔Go | QUICの双方向stream | QUIC DATAGRAM |
| C#↔.NET中継 | LiteNetLib ReliableOrdered | LiteNetLib Unreliable |
| .NET中継↔Go | 内部WebSocket | 同じ内部WebSocketを経由 |
| JS / C#の代替接続 | WebSocket | 同じ信頼性のある接続を経由 |

LiteNetLibの内部中継とWebSocketの代替接続には、信頼性のあるストリームの待機が残ります。能力情報の`boundedLatest`はfalseです。非再送機能があることだけで、混雑時の低遅延を保証しません。

通常起動のサーバーは同一マシンのループバック用です。公開モードは[公開サーバー](deployment.md)を参照してください。QUICは開発用の自己署名証明書を使います。参加者名は認証済みのユーザーIDではありません。

## 相手ごとに直結と中継を選ぶ

`latest` / `live`のアプリ向けAPIは変えず、ブラウザSDKが相手ごとに経路を選びます。互いにWebRTCの直結機能を持ち、接続できた組だけが直結を使います。GoのQUICとC#のLiteNetLib/WebSocketには直結用アダプターがないため、混在する部屋でも中継で通信します。通常メッセージ・共有状態・初回同期・ファイル転送は常にサーバーを通ります。

ブラウザの直結候補は既定で最大2人です。`routing`設定で有効・無効、候補数、相手のリスト、ICEサーバーを指定でき、全員をフルメッシュにする必要はありません。サーバーは現在の部屋の参加者間だけで接続情報を転送し、送信者と接続世代を付けます。退出や再参加で古くなった接続は破棄します。

接続失敗・切断・応答の途絶・送信待ちの増大では、その相手を中継へ戻します。直結と中継の両方から届いた更新には共通の連番判定を使います。これは到達を保証する配送ではなく、切り替え中の`latest` / `live`も欠落し得ます。

JSの`routes()`と`route`イベント、Goの`Routes()`、C#の`Routes`から経路と理由を取得できます。`rttMs`は直結上のping/pongによる往復時間です。中継の相手間遅延や片道遅延を示す値ではありません。通信方式をまたぐ直結と、すべてのNAT環境での接続成立は未対応です。ICEサーバーは既定では未指定で、必要に応じてアプリが用意します。詳細は[経路選択の仕様](../protocol/p2p.md)を参照してください。

## peer間の確実配送を使う

`sendTo(peer, topic, value)`は、宛先の接続世代を固定して受信確認を待つ別APIです。JSは選択済みのpeer接続に信頼性のあるDataChannelを追加し、直結できない相手や直結で進捗がなくなった相手へはコア経由で再送します。Go・C#には直結用アダプターがないため、同じ配送契約で中継します。

大きい値は既定4 MiBまで自動分割し、長さ・SHA-256・順序を検証して一度だけ通知します。送信者・宛先の接続世代・トピックが同じ配送列では、後続を追い越しません。小さい操作用に転送数と容量の一部を予約しますが、同じトピックの先行データは追い越せません。

既定の送信待機量と組立量はそれぞれ8 MiB、通信片12 KiB、受信ウィンドウ64 KiB、同時転送4件、期限30秒、再送5回です。サーバー設定の`peerDelivery`とSDKの対応するオプションから変更できます。受信確認はSDKが受け付けたことを表し、アプリの適用・保存完了とは区別します。開始後に回復不能となった配送列は停止し、再参加とアプリの再同期が必要です。

このAPIはコアの操作履歴へ記録されません。従来の`message`、`checkpoint`、`catchup`、損失を許容する`latest` / `live`は既存の意味を維持します。[配送仕様](../protocol/peer-delivery.md)と[Tonarium向け使用例・移行手順](peer-delivery-guide.md)を参照してください。

JSの`deliveryStats()`、Goの`DeliveryStats()`、C#の`DeliveryStats`で、相手・接続世代・経路・通信種別ごとの送受信、再送、未確認、待ち行列を取得できます。再送により測定対象が曖昧になったRTTはnullです。アプリの処理時間や保存時間を測る統計ではありません。

5人の混在、転送途中の切断、キャンセル、再参加の実施結果は[宛先付き配送の検証記録](peer-delivery-validation.md)にまとめています。この拡張はローカルで確認した段階で、公開サーバーへの追加デプロイは行っていません。

## 設計のうち、今後実装する部分

- 参加ticket、権限付き購読、membershipの安全な復旧、本番向けの暗号・認証。
- 永続保存と、保存済み操作の再起動後の復元。
- 自動再接続、未確定操作の照会、転送の途中再開。
- 購読範囲の動的な変更。
- 通信方式ごとの詳細な統計、帯域予算、公平制御、未達パケットの枠回収。
- 動画フレームの分割・組立、codec合意、依存フレーム管理、デコード・再生。
- Go・C#向けの直結用アダプター、経路の品質比較、Unity/AOT環境での確認。

Tonarium本体の通信差し替えは今回の変更に含みません。ここで通信と初回同期を試し、アプリ側の接続方法を決める段階です。`validation.md`の速度・動画品質の数値は、引き続き未測定の目標です。

## 動作確認

サーバーを起動した状態で、リポジトリのルートから実行します。

```powershell
./scripts/smoke.ps1
```

2026-10-21に、次の小さな確認を実施しました。

| 確認 | 結果 |
| --- | --- |
| Goの単体・結合テスト | 実際のQUIC接続、状態、CAS、削除版、チェックポイント以降の操作、64bit連番、分割転送を確認 |
| JSの結合テスト | WebSocketで操作順序、初回同期ヘルパー、状態、CAS、重複排除、通知、位置・ライブ更新、100 KB転送、キャンセルを確認 |
| C#の結合テスト | 実際のLiteNetLib接続、状態、競合、途中参加、64bitの位置更新、約200 KBの双方向転送、空ファイルを確認 |
| ChromeのWebRTC接続 | 2画面で同じ描画・操作番号を確認。保存したチェックポイントから再参加して復元 |
| JS WebRTC・C# LiteNetLib・Go QUICの同時接続 | 同じ`mixed`部屋で相互配送。ブラウザの描画操作18・19と位置更新をC#・Goの両方で受信。C#とGoの操作も互いに受信 |

自動分割の追加後、同じスクリプトで以下も確認した。

- GoとJSで1 MiBの通常メッセージ、共有状態、参加時の状態、checkpoint/catchupを復元。
- C#のLiteNetLibとWebSocket間で100 KBの通常メッセージ、初期同期、snapshot、checkpoint/catchupを復元。
- 大容量転送中も別種類の通信を進め、同じメッセージ列の順序を維持。
- ハッシュ不一致、容量超過、受信の停滞、期限切れ、キャンセルで、途中データを公開せずに予約領域を解放。
- SDKのアプリ受信待ち、送信待ち、サーバーの保持データを容量上限内で管理。

経路選択の追加後、次も確認した。

- JSの経路管理テストで候補数の上限、接続期限、応答途絶、混雑時の中継復帰、古い接続世代・接続試行の排除、重複排除を確認。
- サーバーのテストで参加者情報、接続情報の送信者確定、宛先指定、退出した相手の除外、サイズ・回数制限を確認。
- Go・C#で参加者ごとの中継経路情報と送受信数を確認。
- Chromeの2画面にGo QUICとC# LiteNetLibを加えた部屋で、ブラウザ間の直結とネイティブ向け中継を同時に確認。`latest` / `live`の両方が届いた。
- 片方のブラウザで直結を無効にした後、もう片方が中継へ戻り、同じAPIの送信が届くことを確認。

確認は少人数・短時間の試験です。公開ブラウザの接続と大容量メッセージは[公開サーバーの確認結果](deployment.md#確認結果)を参照してください。回線飽和時の遅延、異なるNAT間での直結、長時間のメモリ挙動、実動画の再生は測定していません。
